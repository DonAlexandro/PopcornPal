Explicit Gameplay-driven Filter in Game Picker

Summary: the game selection logic now filters gameplay picks by the Notion property Gameplay-driven = true, instead of inferring gameplay from Story-driven = false. This lets a game be both story and gameplay, and naturally skips games where both flags are false.

Assumption used for this explainer: the target change is the latest diff in src/services/notion.ts where style filtering for game fetch was changed.

1. Background

Mental model: the bot asks the user for platform and game style, then queries Notion for one matching game, enriches it with IGDB details, and sends a recommendation.

Telegram handlers

Collects user choice and maps button text to style values story or gameplay.

References: src/bot/handlers.ts lines 422-433 and 742-755.

Notion query layer

Builds filters for status, platform, and style; returns one random page.

References: src/services/notion.ts lines 104-190.

Data semantics

Story-driven and Gameplay-driven are two independent checkboxes, not strict opposites.

Consequence: a game can have both true.

Step A
User presses Story-driven or Gameplay-driven in Telegram.
Step B
Handler maps button text to styleChoice and calls getRandomGameFromNotion(platform, style).
Step C
Notion query applies three constraints: style filter, status filter, platform filter.
Step D
One random page is sampled and returned; bot fetches IGDB details and responds.
Prior behavior issue: gameplay picks were effectively all non-story games, which accidentally excluded games that are both story and gameplay, and included games where both flags were false.

2. Intuition

The fix is simple: treat each checkbox as its own meaning. For a gameplay request, demand Gameplay-driven = true. For a story request, demand Story-driven = true.

Before

Filter logic for style was tied only to Story-driven: 

story request    => Story-driven = true
gameplay request => Story-driven = false

Gameplay became a leftover bucket.

After

Filter logic uses explicit property per style: 

story request    => Story-driven = true
gameplay request => Gameplay-driven = true

Now both-true games are valid for both styles; both-false games match neither.

3. Code

This walkthrough is grouped by execution flow rather than by raw file order.

Group 1: User input chooses style

Telegram buttons are Story-driven and Gameplay-driven. The handler maps them to internal values story or gameplay, then calls the fetch function. 

// src/bot/handlers.ts (422-433)
if (text !== "📖 Story-driven" && text !== "🎮 Gameplay-driven") {
  await messenger.sendMessage(chatId, "Choose game type:", gameTypeKeyboard);
  return;
}

await handleFindGame(
  messenger,
  chatId,
  sessionStore,
  userState.platform,
  text === "📖 Story-driven" ? "story" : "gameplay",
);

Group 2: Style filter is now explicit

The main change is creation of styleFilter in the Notion service.

// src/services/notion.ts (136-149)
const styleFilter =
  styleChoice === "story"
    ? {
        property: "Story-driven",
        checkbox: { equals: true },
      }
    : {
        property: "Gameplay-driven",
        checkbox: { equals: true },
      };
Invariant: style choice always maps to a positive checkbox test on the corresponding property.

Group 3: Query combines style with existing constraints

Only style predicate changed. Status and platform behavior are unchanged. 

// src/services/notion.ts (151-175)
filter: {
  and: [
    styleFilter,
    {
      or: [
        { property: "Status", status: { equals: "Backlog" } },
        { property: "Status", status: { equals: "Plan to play" } },
      ],
    },
    platformFilter,
  ],
}

Group 4: Observable behavior after query

If no results match all constraints, code still throws No games found. That user-visible behavior is unchanged; only matching set changed. 

// src/services/notion.ts (178-182)
const pages = response.results;
if (pages.length === 0) {
  throw new Error("No games found");
}
